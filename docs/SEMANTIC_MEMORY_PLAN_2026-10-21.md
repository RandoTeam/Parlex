# Semantic Memory — EmbeddingGemma 2 для Parlex

| | |
|---|---|
| Статус | Проектирование / следующий дифференциатор |
| Модель | Google **EmbeddingGemma 2** (300M, 100+ языков), on-device через LiteRT |
| Дата | 2026-10-21 |
| Связанный аудит | `docs/AUDIT_AND_RECOVERY_PLAN_2026-10-21.md` |

## 1. Зачем это приложению

Parlex уже хранит историю переводов, диалоги, словарь и избранное. Сейчас поиск по ним — `LIKE '%query%'` (`TranslationDao.searchTranslations`, `DialogueDao`), поэтому:

- нельзя найти «тот разговор, где мы обсуждали цену такси», если там было «сколько стоит доехать»;
- нельзя переиспользовать удачные переводы как translation memory;
- нельзя сгруппировать одинаковые фразы в камере/на экране;
- нельзя построить «поиск по смыслу» по экранным блокам и документам.

EmbeddingGemma 2 даёт локальные векторы без облака и без отправки текста. Это прямо усиливает позиционирование Parlex: **offline, sovereign, no telemetry**, но с современным semantic search.

## 2. Что именно можно сделать (по возрастанию сложности)

### 2.1 Semantic History Search (первый шаг)

- Пользователь пишет «такси аэропорт», находит перевод/диалог, где было «трансфер в аэропорт», даже без точного слова.
- Гибридный поиск: `BM25/LIKE` + cosine по векторам, ранжирование `score = 0.35 * lexical + 0.65 * semantic`.
- Фильтры: язык, дата, избранное, источник (текст/диалог/камера/экран).
- Работает полностью офлайн; индекс строится один раз при сохранении записи.

### 2.2 Translation Memory (второй шаг)

- Перед переводом ищем 1–3 похожих прошлых перевода (cosine > 0.90) и подмешиваем их в prompt LLM как few-shot или в глоссарий.
- Для NMT (ML Kit) — используем как подсказку «так уже переводили» в UI, не влияя на модель.
- Плюс: консистентность терминов, брендов, имён, повторяющихся фраз интерфейса.
- Обязательно: пользователь может отключить, чтобы «не залипать» на старом переводе.

### 2.3 Semantic Screen Blocks (экранный перевод)

- Дедупликация блоков между кадрами/скроллом: одинаковый смысл, разный OCR-шум → один перевод.
- Поиск по переведённому экрану: «где тут цена», «найди адрес», «покажи только кнопки».
- Кэш переводов по embedding-хешу: если блок похож на уже переведённый (cosine > 0.97), берём готовый перевод, не гоняем NMT.
- Группировка блоков в абзацы/карточки по семантике, а не только по координатам.

### 2.4 Semantic Camera / Documents

- Поиск по распознанным документам: «чек из аптеки за март», «меню с пастой».
- Кластеризация строк меню/таблиц, чтобы перевод не «рассыпался».
- Автоматическое определение типа документа (меню, вывеска, инструкция, визитка) → выбор промпта/модели.
- Похожие кадры: не переводить один и тот же документ повторно.

### 2.5 «Ask your history» (RAG, поздний шаг)

- Вопрос к истории: «Что мы решили по отелю?», «Сколько стоил билет?».
- Retrieval: top-K embeddings → локальная LLM (Hy-MT2 / Gemma) отвечает с цитатами.
- Только opt-in, только по кнопке, с явным предпросмотром найденных фрагментов; никакой сети.
- Ограничение: не отправлять в модель больше N токенов; всегда показывать источники.

### 2.6 Dictionary / Learning

- Семантически похожие слова и примеры (не только точное совпадение).
- Подбор примеров под контекст пользователя.
- Кластеризация ошибок/частых фраз для «умных» карточек повторения.

### 2.7 Model Manager и Travel Packs

- Рекомендация моделей по языкам/устройству на основе эмбеддингов описаний (менее важно).
- Проверка целостности/дублей `.parlex-fast` архивов по хешу содержимого.
- Поиск по каталогу моделей на естественном языке.

## 3. Техническая архитектура

```
Text (history / dialogue / screen block / document)
        │
        ├── chunker (1 запись = 1 chunk, длинные документы 400–800 символов)
        ├── prompt prefix: "task: search result | query: " / "title: ..."
        ▼
EmbeddingGemma 2 (LiteRT, 256/512 dim, INT8, CPU/GPU/NPU)
        ▼
SQLite/Room: semantic_embeddings(entityType, entityId, lang, vector BLOB, modelVersion, updatedAt)
        ▼
Vector search: brute-force cosine (N < 50k) или IVF/HNSW при росте
        ▼
Hybrid ranker + UI
```

### 3.1 Модель и рантайм

- **EmbeddingGemma 2** (или EmbeddingGemma 300M, если вторая версия ещё не упакована для LiteRT) — 300M, 100+ языков, ~200 MB в INT8.
- LiteRT-LM / MediaPipe LLM Inference: проверить наличие `embed` API в `com.google.ai.edge.litertlm:litertlm-android:0.16.0`; если нет — использовать LiteRT `.tflite` + собственный tokenizer (SentencePiece) или ONNX Runtime (уже есть `libonnxruntime.so` через sherpa).
- Не тащить вторую тяжёлую модель в базовый APK: скачивание по кнопке в Model Manager, отдельная секция «Semantic Memory».
- Размерности: 256 (быстро, ≤1 ms/запись на CPU) или 512 (точнее). Хранить `modelVersion` и `dim`; при смене модели — переиндексация.
- Батчинг: 16–32 текста за проход, off-main-thread, с ограничением по памяти.

### 3.2 Схема БД (v6)

```sql
CREATE TABLE semantic_embeddings (
  id INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL,
  entityType TEXT NOT NULL,      -- translation | dialogue_message | screen_block | document
  entityId INTEGER NOT NULL,
  language TEXT NOT NULL,
  modelVersion TEXT NOT NULL,
  dim INTEGER NOT NULL,
  vector BLOB NOT NULL,          -- Float32 little-endian или Int8 + scale
  textHash TEXT NOT NULL,        -- дедуп повторной индексации
  updatedAt INTEGER NOT NULL
);
CREATE UNIQUE INDEX index_semantic_entity ON semantic_embeddings(entityType, entityId, modelVersion);
CREATE INDEX index_semantic_hash ON semantic_embeddings(textHash);
```

- Миграция `5 -> 6` в `DatabaseMigrations` (не destructive).
- Вектор хранить как `FloatArray` → `ByteBuffer`; для 512 dim это 2 KB/запись; 50k записей ≈ 100 MB — нужен лимит/очистка.
- Альтернатива: хранить Int8-квантованные векторы (512 B) + scale; точность достаточна для поиска.
- Для больших документов — отдельная таблица chunks с `parentId`.

### 3.3 Индексация

- Триггеры: после вставки перевода/сообщения/документа; батч-джоб при старте (если модель доступна и включена).
- Очередь в `SemanticIndexWorker` (WorkManager) или корутина с ограничением 1–2 потоков.
- Не индексировать:
  - пустые/короткие (<8 символов) строки;
  - точные дубликаты (textHash);
  - пароли/номера карт (фильтр по regex, как в screen noise filter, но не удалять — пропускать индексацию).
- При выключенной функции — не хранить embeddings и удалить существующие (кнопка «Очистить индекс»).

### 3.4 Поиск

- Query embedding + cosine.
- Порог: 0.62 для «похоже», 0.82 для «почти то же».
- Гибрид: lexical score (нормализованный BM25/`LIKE`) + semantic; для коротких запросов больше вес lexical.
- Дедуп результатов по `textHash`/`parentId`.
- Для 50k+ записей — IVF/HNSW; до этого brute force на Kotlin с `FloatArray` и `dot` за O(N) приемлем (50k × 512 ≈ 25M операций, ~10–30 ms на современном CPU).
- Кэш query→topK в памяти (LRU 64).

### 3.5 Приватность и ресурсы

- Всё локально, без сети; модель скачивается как остальные.
- Индекс не попадает в backup (`allowBackup=false` уже включён).
- Явный переключатель «Семантический поиск» в настройках; по умолчанию **выключен** (лишние ~200 MB и батарея).
- Ограничение: не индексировать, если батарея < 15% и не на зарядке (настройка).
- Показывать пользователю, сколько места занимает индекс и кнопку очистки.

## 4. UX-идеи

- **Search bar с двумя режимами**: «Слова» / «По смыслу» (иконка Sparkle).
- **Похожие переводы** под результатом: «Вы уже переводили это как …» с кнопкой «Использовать».
- **Диалоги**: «Найти в разговоре» → подсветка реплик, а не просто список.
- **Экран**: после перевода — «Найти на экране» (цена/адрес/кнопка) с подсветкой блока.
- **Камера**: «Похожие документы» в истории; «Открыть прошлый чек».
- **TQI/QA**: semantic duplicate detection как метрика качества экстракции.

## 6. Риски

- Модель 300M и индекс съедают RAM/диск → обязательный opt-in и лимиты.
- Эмбеддинги многоязычные, но качество на коротких UI-строках ниже → гибрид с lexical.
- При смене модели нужна переиндексация; версионировать.
- Нельзя индексировать чувствительные данные без согласия; фильтры и выключатель.
- LiteRT API для embeddings может отличаться от LLM API; проверить на устройстве до реализации S1.
- Не обещать «Google Embedding 2» в UI, если используется EmbeddingGemma: писать «EmbeddingGemma 2 (on-device)».

## 7. Что проверить перед стартом

1. Есть ли в `litertlm-android:0.16.0` публичный API `embed`/`EmbeddingModel`; если нет — скачать `.tflite` и токенизатор.
2. Замерить latency/размер EmbeddingGemma 2 INT8 на OnePlus 13 (CPU/GPU/NPU).
3. Проверить лицензию Gemma (Gemma Terms) и добавить в `THIRD_PARTY_NOTICES.md`.
4. Согласовать с `allowBackup=false` и очисткой истории.
5. Определить, индексировать ли экранные блоки только в памяти (не сохранять на диск) — вероятно, да, для приватности.
